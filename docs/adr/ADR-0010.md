# ADR-0010：数据快照

- **状态：** accepted（2026-11-06，项目负责人按评审稿建议通过）
- **日期：** 2026-11-06
- **评审人 / 批准人：** 项目负责人
- **规格书出处：** 第 16 节（章节映射见 [../README.md](../README.md)）

## 背景

研究与估值必须可复现：同一输入、同一模型版本，应得到同一输出。行情数据量大且可能被供应商修订，财务事实为只追加记录。

## 候选方案

| 方案 | 说明 | 结论 |
|---|---|---|
| A 复制数据进快照 | 把全部输入拷贝一份 | 放弃：冗余严重，尤其是行情 |
| B 引用 + 哈希 | 快照清单逐行引用有 UUID 的记录，行情按区间引用，并保存内容哈希 | **采纳** |
| C 仅用 `as_of` 时间查询 | 不建快照 | 放弃：无法证明当时读到了哪个修订版本 |

## 决定（规格书推荐）

`data_snapshots` + `data_snapshot_items` 不可变（触发器拒绝 UPDATE/DELETE）；财务事实逐行引用，`market_bars` 按区间引用并带 `observed_at_cutoff`；清单内容生成规范化哈希。

## 理由

- 引用比复制节省空间，哈希保证引用内容未变；
- 依赖“事实只追加 + 行情带 `revision_no`”（见 12.8）才能在数据被修订后仍可复现。

## 后果

- 许可到期需清除数据时，必须经受审计的维护流程，并先把受影响快照标记为不可复现；
- 快照生成成本随引用数量增长；
- 规范化哈希规则必须固定（Phase 1 计划 D10）。

## 测试影响

- 哈希可复算；
- 快照与事实表的 UPDATE/DELETE 被触发器拒绝；
- 用快照复跑估值得到相同结果；
- 行情被修订（新 `revision_no`）后，旧快照仍复现。

## 评审结论（2026-11-06）

- **区间引用的哈希算法与成本：** 按 `bar_time` 排序，对区间内每行的规范化内容求哈希，再对哈希序列整体求哈希；在快照生成时一次算好并保存，复核时重算。日线规模下成本可接受，Spike S4 记录实测耗时。
- **快照保留期限：** 作为用户研究产物长期保存（与 OPEN_QUESTIONS #6 的临时策略一致）；只有许可到期等合规原因才经受审计流程清除，并先标记为不可复现。
