# ADR-0001：模块化单体

- **状态：** accepted（2026-11-06，项目负责人按评审稿建议通过）
- **日期：** 2026-11-06
- **评审人 / 批准人：** 项目负责人
- **规格书出处：** 第 5 节、8 节（章节映射见 [../README.md](../README.md)）

## 背景

GEI 需要 Web、REST、Worker、Scheduler、MCP 多个入口，团队规模小，而快照、幂等、状态机等关键机制都依赖同一数据库内的事务一致性。需要在“尽早拆分”与“过早引入分布式复杂度”之间取舍。

## 候选方案

| 方案 | 说明 | 结论 |
|---|---|---|
| A 模块化单体 | 一个代码库、清晰分层；进程上分为 api / worker / scheduler / 独立 MCP 入口 | **采纳** |
| B 微服务 | 按数据、估值、Agent 等拆成独立服务 | 放弃：跨服务事务与一致性成本高，MVP 无收益 |
| C 单进程 | 不设 Worker，请求内同步执行长任务 | 放弃：研究 Run 必须异步，不能长期阻塞请求 |

## 决定（规格书推荐）

FastAPI + Worker + Scheduler + 独立 MCP 入口，按模块边界组织代码，MVP 不引入微服务、Kubernetes 或复杂消息中间件。

## 理由

- 数据快照、Clean-before-Write 幂等、Run/Task 状态机都需要同库事务，拆分会引入分布式事务；
- 边界靠 Ports & Adapters 与导入契约守住，而不是靠网络；
- 部署形态（Windows 本地 Docker、Linux 单机）本身就是单机多进程。

## 后果

- 必须用工具强制分层（计划中的 `import-linter`），否则单体会退化为泥球；
- `api` 与 `worker` 共用代码包，需通过 `code_version` 保证两者版本一致；
- 将来若拆分，候选拆分点是 Provider 灌库与 Agent 编排，因其无需与估值共享事务。

## 测试影响

- `import-linter` 契约：`packages/domain` 不得导入 FastAPI、SQLAlchemy、Celery、供应商 SDK；
- Compose 服务清单测试：MVP-1 默认启动集不含 `mcp`。

## 评审结论（2026-11-06）

- **API、Worker 是否同代码包、同镜像：** 是。`api`、`worker`、`scheduler` 使用同一镜像、不同启动命令；`code_version` 在构建时由 Git 提交号写入，Run 记录它，保证 API 与 Worker 版本一致且可查。
- **MCP 独立进程是否在 MVP-2 前都不建：** 是。MVP-1 不创建 `apps/mcp-server`，Compose 中也不出现 `mcp` 服务。
